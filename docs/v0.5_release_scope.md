# nanoprot v0.5 — model release scope

**Status: spec (pre-training). This document is the single source of truth for
the v0.5 release grid; the config generator and Slurm scripts implement it.**

v0.5 is the first version that produces *artifacts* rather than code: a matrix
of pretrained checkpoints + reproducible model cards, released on the
HuggingFace Hub. It is the protein-LM analogue of the Pythia model suite.

---

## 1. Resolved design decisions

Three forks were resolved before any GPU time is spent. Each is recorded with
its rationale so the choice is auditable.

### 1.1 Tokenizer: unified 33-token residue alphabet (V = 33) for **all** archs

Earlier versions used a 50,256-token BPE vocabulary for the autoregressive
archs (`gpt2`, `mamba`) and the 33-token ESM-2 alphabet for `esm2`. The release
unifies **down** to the residue alphabet for every architecture.

**Why (in order of force):**

1. **Per-residue label alignment.** The downstream probes (DSSP secondary
   structure, active/binding sites, disorder) carry *per-residue* labels. A BPE
   token spans several residues, so a learned feature cannot be cleanly mapped
   to a single residue's label — the alignment is many-to-one and the probe is
   ambiguous. Residue-level tokenization makes per-residue probing **exact**.
   This is the decisive argument: nanoprot exists to support interpretability,
   and BPE breaks the residue↔feature correspondence that interpretability
   needs.
2. **Cross-architecture probing (v0.6) requires shared tokenization.** Comparing
   learned features across architectures is incoherent if the input
   tokenization differs.
3. **Parameter count ≈ transformer capacity.** With V = 33 the embedding/​
   lm_head terms (∝ V·d) become negligible, so a model's parameter count
   reflects its actual transformer capacity rather than a giant vocabulary
   table. This makes the scaling grid clean.
4. **Field standard.** ESM-2 — the comparison anchor — *is* the 33-token
   alphabet. BPE on proteins is non-standard (proteins lack natural subword
   structure).

**Consequence (the part that is the first author's call, now approved):** the
previously documented "1.17 B `gpt2_d20`" reference model was a BPE-50k artifact
whose size was dominated by vocab-indexed ResFormer value embeddings (643 M of
the 1.17 B). At V = 33 those collapse to < 1 M, so that specific 1.17 B model
*ceases to exist*. It is **not** part of the release grid. It survives only as an
optional **tokenization-ablation** config (`gpt2_d20_uniref50_bpe.yaml`), should
we ever want to study BPE-vs-residue. **This does not touch the thesis**, which
is a separate publication and keeps its own BPE-50k `prot_*` models.

> Engineering note: vocab-indexed ResFormer value embeddings are vestigial at
> V = 33. We **do not** redesign the `gpt2` architecture for v0.5 — the term is
> harmless (tiny, still initialised). A comment marks it; any redesign is a
> separate, later change validated at multiple depths.

### 1.2 Comparability claim (stated honestly, not hidden)

- **`gpt2` ↔ `mamba`: directly comparable.** Same vocabulary, same AR objective,
  same data budget rule ⇒ **bits-per-residue (bpr) is a clean controlled
  comparison.** This is the high-value head-to-head and the primary scientific
  output of the suite.
- **AR ↔ `esm2` (MLM): NOT bpr-comparable.** AR bpr measures next-residue
  compression; the MLM metric is a pseudo-perplexity over *masked* positions —
  a different quantity. `esm2` is released as the encoder family and compared on
  **downstream / probing tasks (v0.6)**, with its MLM metric reported
  separately. We never claim "bpr is comparable across all three."

- **`weight_decay` held uniform (0.1) across all archs.** "Controlled" means
  *every* hyperparameter except the architecture is matched — including
  regularization. The per-arch preset values (gpt2 0.28, esm2 0.01, mamba 0.0)
  are neither matched nor protein-tuned (gpt2's 0.28 is inherited from the
  nanochat English-text speedrun), and weight decay is *applied* (to the Muon
  matrix params), so a 28× gpt2/mamba gap would be a second confounding variable
  on top of architecture. We use a single conventional value (0.1; GPT-3 / Llama
  / OLMo) so the gpt2↔mamba conclusion survives a reviewer pointing at the
  optimizer column. LRs are already matched (muP-transferred).

- **AR seed variance is initialization-only (a lower bound).** The AR data
  loader (`dataloader.py`) is fully deterministic — best-fit greedy packing, no
  shuffle, no seed — so for `gpt2`/`mamba` the 3 seeds differ only in model
  initialization, not data order. The MLM loader *does* consume the seed (for
  masking), so `esm2` seeds vary in both. Report AR variance bands as
  **initialization variance**, not full run-to-run variance; they under-state
  true variability. (Fix path for a later version: seed-dependent shard/document
  shuffling in the AR loader.)

### 1.3 Architecture comparison method: **scaling curves, not single points**

Architectures are compared the Kaplan/Hoffmann way — by their **scaling curves**
(metric vs. parameters, metric vs. training compute) across the ladder — not by
contriving a single equal-parameter cell. We therefore do **not** distort each
arch's natural width rule to force identical parameter counts; we let each arch
follow `d_model = 64 · depth` (AR) / the canonical ESM-2 grid (`esm2`), pick the
depth nearest each target, and **report the actual parameter count per cell**.

## 2. The release grid

Four scale rungs mirror ESM-2's published ladder (≈ 8M / 35M / 150M / 650M).
Three architectures. **12 cells × 3 seeds = 36 training runs.**

Constants across every cell: `max_seq_len = 512`, `vocab_size = 33`,
`param_data_ratio = 12` (Chinchilla-style; data scales with params),
`total_batch_size = 524,288` residues/step.

| arch | scale | depth | d_model | n_heads | **actual params** | train residues | steps |
|---|---|---:|---:|---:|---:|---:|---:|
| gpt2 | XS | 6 | 384 | 6 | 10.7 M | 0.13 B | 244 |
| gpt2 | S | 9 | 576 | 9 | 36.0 M | 0.43 B | 823 |
| gpt2 | M | 14 | 896 | 14 | 135.1 M | 1.62 B | 3,093 |
| gpt2 | L | 23 | 1472 | 23 | 598.7 M | 7.18 B | 13,703 |
| mamba | XS | 7 | 448 | — | 9.0 M | 0.11 B | 206 |
| mamba | S | 11 | 704 | — | 34.6 M | 0.42 B | 792 |
| mamba | M | 18 | 1152 | — | 150.7 M | 1.81 B | 3,449 |
| mamba | L | 29 | 1856 | — | 627.9 M | 7.54 B | 14,372 |
| esm2 | XS | 6 | 320 | 20 | 7.4 M | 0.09 B | 169 |
| esm2 | S | 12 | 480 | 20 | 33.2 M | 0.40 B | 760 |
| esm2 | M | 30 | 640 | 20 | 147.5 M | 1.77 B | 3,376 |
| esm2 | L | 33 | 1280 | 20 | 648.9 M | 7.79 B | 14,852 |

The **S / M / L** rungs are matched within ~10 % across archs (the rungs that
carry the comparison); **XS** is looser (~7–11 M) because the embedding floor
differs — acceptable, since comparison is by curve, not point. `head_dim = 64`
for the AR archs (clean `d = 64·depth` granularity); the ESM-2 column uses the
canonical head counts of the public release.

Total to train the whole release: **29.3 B residues × 3 seeds ≈ 87.8 B
residues.** (Compute is not a binding constraint for this project.)

### Seeds

**3 seeds per cell.** Single-seed comparisons cannot distinguish a real
architecture gap from seed noise; 3 seeds give variance bands and let the suite
make *statistical* claims ("mamba-M < gpt2-M in bpr, p < …"). Consistent with the
existing thesis sweep methodology. All three seeds are released (Pythia-style
seed variants); **seed 0 is the headline / default download**, and the model
card reports mean ± std across seeds.

## 3. Artifacts & naming

- **Model name:** `nanoprot-{arch}-{scale}` (e.g. `nanoprot-mamba-M`).
- **HuggingFace repo:** one repo per (arch, scale) — `ygzdvr/nanoprot-{arch}-{scale}`
  (mirrors Pythia's one-repo-per-model). Seed variants live on branches
  `seed0` (= `main`), `seed1`, `seed2`.
- **Local checkpoint dir:** `$NANOPROT_BASE_DIR/release/nanoprot-{arch}-{scale}-s{seed}/`
  containing `model_{step:06d}.pt`, `meta_{step:06d}.json`,
  `optimizer_{step:06d}.pt` (final step only kept for release; intermediate
  checkpoints optional via `save_steps`).
- **Model card:** `README.md` at the repo root, auto-generated (§5).

## 4. Execution plan (Slurm) — BUILT

All tooling below is implemented and tested (CPU-validated; GPU runs are the
user's to `sbatch`). Run order: (1) generate configs, (2) calibrate, (3) train,
(4) make cards.

1. **`scripts/gen_release_configs.py`** — single source of truth. Emits the
   **36** release YAMLs (`nanoprot-{arch}-{scale}-s{seed}.yaml`, 12 cells × 3
   seeds), 3 calibration probes (`calib/calib-{arch}.yaml`), and a
   `MANIFEST.tsv`, into `configs/release/`. Every emitted config is round-tripped
   through `NanoprotConfig` before writing, so a schema error surfaces here, not
   13k steps into a GPU run. `--intermediate` adds log-spaced training-dynamics
   checkpoints (off by default). Never hand-edit the YAMLs — regenerate.
2. **`runs/calibrate_throughput.slurm`** — 3-task array (one per arch, S scale,
   ~120 steps), prints `tok/s`. Run first; size `--time` / `device_batch_size`
   to the measured throughput. (GPU wall-clock can't be estimated a priori,
   especially at small scale where runs are latency- not FLOP-bound.)
3. **`runs/train_release.slurm`** — 36-task array (`--array=0-35%8`). **Resumable
   / skip-completed**: a cell is skipped when its newest meta has
   `step == num_iterations`. `WANDB_MODE=offline`; sync with
   `wandb sync --sync-all wandb/` after. `--time=12:00:00` (≥ 02:00:00 keeps the
   >25-task array on `gpu-short`, not `gpu-test`). Cluster paths are
   env-overridable (`NANOPROT_REPO`, `NANOPROT_VENV`, `NANOPROT_BASE_DIR`).
4. **`scripts/make_model_card.py`** — generates HF `README.md` per model from the
   self-describing `meta_*.json`, aggregating **mean ± std across sibling seeds**,
   and writes a self-contained `config.yaml` next to the weights. `--release-root`
   does the whole grid.

### Implementation decisions made during the build

- **Tokenizer = `esm2` (33-token) for all archs.** There is no separate
  "residue" tokenizer in the schema; the 33-token ESM-2 alphabet *is* the
  residue alphabet. The data builder dispatches tokenizer and objective
  independently, so `objective: ar` + `tokenizer: esm2` is valid and tested.
- **esm2 uses SDPA (`flash_attention: false`); AR uses FA3.** FA3 only engages
  on Hopper+bf16 and the kernel supports head_dim ∈ {64, 128}; the esm2 small
  rungs have head_dim 16/24/32, so they must use SDPA (exact, bidirectional-safe;
  speed is irrelevant under unlimited compute). gpt2/mamba use head_dim 64.
- **`device_batch_size`** defaults: XS/S=32, M=16, L=8 (microbatch only;
  `total_batch_size` is fixed at 524,288, so this trades memory vs. grad-accum,
  never the math). Calibration may raise these for speed.
- **Self-describing checkpoints.** `loop._save` now records `n_params`,
  `flops_per_token`, `total_flops`, `total_residues`, `world_size`,
  `train_time_sec`, the full resolved `config`, and the real package `version`.
  The card generator reads these directly (no model load). Wired up
  `checkpointing.save_steps` (previously defined but unused) for intermediate
  checkpoints. Guarded by `test_checkpoint_meta_is_self_describing`.
- **Known limitation (flagged, not yet fixed):** the *internal* checkpoint loader
  `nanoprot.training.checkpoint.build_model` is gpt2+bpe-hardcoded (a v0.2
  remnant) and cannot load esm2/mamba. The **release** load path does not use it
  — the model card ships a registry-based snippet (`nanoprot.models.build_model`
  + the embedded config), verified to `load_state_dict(strict=True)` and forward
  for all three archs. Generalising the internal loader is the recommended next
  task (needed before the chat/inference path supports multi-arch).

## 5. Model-card schema

Every released checkpoint ships a HuggingFace model card (`README.md`)
**auto-generated** by `scripts/make_model_card.py` from three reproducible
inputs — the resolved config YAML, `meta_{step}.json`, and the eval-results
JSON — so the card never drifts from the artifact. The schema:

### YAML front-matter (HF-parsed)
```yaml
license: mit
library_name: nanoprot
tags: [protein-language-model, proteins, uniref50, nanoprot, <arch>]
datasets: [uniref50]
metrics: [bits-per-residue]          # or masked-perplexity for esm2
model-index:
  - name: nanoprot-<arch>-<scale>
    results:
      - task: {type: masked-language-modeling | causal-language-modeling}
        dataset: {name: UniRef50 (held-out shard), type: uniref50}
        metrics:
          - {type: bits-per-residue, value: <val_bpr>}   # AR archs
```

### Body sections (fixed order)
1. **Title + one-line summary** — `nanoprot-<arch>-<scale>`: an `<arch>`
   protein LM, `<params>` parameters, trained on `<residues>` UniRef50 residues.
2. **Model details** — arch, objective (AR/MLM), depth, d_model, n_heads,
   d_state/expand (mamba), max_seq_len, vocab (33-token residue alphabet),
   precision, parameter count (exact).
3. **Training** — data (UniRef50 release pinned), tokenizer, optimizer
   (Muon+AdamW + LRs), batch size, steps, param-data ratio, total residues,
   total FLOPs (from `meta`), wall-clock, hardware, **seed** + sibling seeds.
4. **Evaluation** — held-out val_bpr (AR) / masked-perplexity (esm2),
   **mean ± std across the 3 seeds**, and the position on the arch's scaling
   curve. Explicit comparability note (§1.2): bpr comparable to other AR
   nanoprot models only.
5. **Intended use & limitations** — research / representation extraction /
   probing; not for clinical use; trained only on UniRef50.
6. **How to load** — `nanoprot` + HF snippet; which checkpoint file.
7. **The nanoprot suite** — table linking the sibling models (all archs ×
   scales), so each card situates itself in the grid.
8. **Citation** — repo BibTeX + (eventually) the paper.
9. **Reproducibility** — exact config YAML (embedded), commit hash, command to
   re-train.

## 5b. Data prerequisite (must be satisfied before any run)

The release configs set `data.shard_dir = ${NANOPROT_BASE_DIR}/uniref50_parquet`.
**UniRef50 parquet shards must be staged there** (each a parquet with a `text`
column of sequences; the last shard is held out for validation).

**Build the corpus** (nanoprot ships its own prep — `scripts/prepare_uniref50.py`
+ `runs/prepare_uniref50.slurm`):
1. On a **login node** (compute nodes have no internet), download the FASTA:
   `wget https://ftp.uniprot.org/pub/databases/uniprot/uniref/uniref50/uniref50.fasta.gz
   -O $NANOPROT_BASE_DIR/uniref50.fasta.gz` (~14 GB).
2. `sbatch runs/prepare_uniref50.slurm` (CPU partition) — streams the FASTA into
   ~200 globally-shuffled parquet shards, upper-cased and normalised to the
   33-token ESM-2 alphabet, with multiple row-groups per shard for DDP.
   (`MAX_SEQUENCES=200000 NUM_SHARDS=8 sbatch …` makes a quick subset to smoke-
   test the pipeline first.) Guarded by `tests/test_prepare_uniref50.py`.

Two traps, now guarded:

- **Do not use the built-in downloader.** `python -m nanoprot.data.dataset`
  fetches the *English ClimbMix* corpus (a nanochat leftover), not proteins.
- **`data.shard_dir` is now live.** It was previously ignored — the loader read a
  module-level `DATA_DIR` (env `NANOPROT_DATA_DIR`, default = ClimbMix). v0.5
  plumbs `shard_dir` through `build_data_loader → loader → list_parquet_files`,
  and a *missing* explicit `shard_dir` now raises a clear `FileNotFoundError`
  instead of silently falling back to other data. Guarded by
  `tests/test_data_shard_dir.py`. The Slurm scripts also pre-flight-check the
  data directory and refuse to launch without it.

The `esm2` (33-token) tokenizer needs no training step — it is a hardcoded
alphabet, so there is no tokenizer-prep prerequisite.
